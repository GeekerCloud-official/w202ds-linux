# W202DS VPU 的 V4L2 适配

2026-11-08，V10 新增受限 H.264 High、8×8 transform 和 scaling matrix。
92 项标准 Request（84 项像素、8 项拒绝，成功解码 520 帧）及 FFmpeg VA-API
9 组 65 帧通过逐字节 NV12 核对。V9 的 Baseline/Main 浏览器短测保留为历史结果；
本轮没有把浏览器或 B 站的 High 播放标为通过。
当前是受限 H.264 解码器；不把节点注册、构建成功或软件回退当作硬解验收。

## 当前实现

电源、VAU IOMMU 和 codec 三件模块分别管理电源域、地址映射和作业。
`w202_vpu_video.c` 对外提供 H264_SLICE 输入、NV12 输出、vb2 和 Media Request；
`w202_vpu_h264.c` 将标准 H.264 controls 转为寄存器；共享资源接口负责独占、
DMA-BUF attachment、IRQ、reset、runtime PM 和失败 quarantine。
旧特权 `/dev/sprd_vsp` 与 Bionic 原厂 worker 保留作对照，原生标准链路不使用原厂 AVC 库。

受限格式为 progressive 8-bit 4:2:0、Baseline/Main/High、单 slice IDR/P，及 Main/High
非参考 spatial-direct B，每个活动列表一个短期参考。temporal direct、参考 B、加权、
多活动参考、多 slice、field、10-bit 和其他 chroma format 尚不支持，均显式拒绝。
High 允许 8×8 transform；SCALING_MATRIX 接受六张 4×4 和 4:2:0 使用的两张 8×8
raster 矩阵，所用系数必须为 1..255。未启用 8×8 时不要求其列表有效；4:2:0
不读取其余四张 8×8 列表。带矩阵标记的 Request 必须明确携带该 control，不能沿用旧 Request。
DECODE_MODE／START_CODE 允许写回唯一默认值，profile 菜单只读，声明到 High 并跳过 Extended。

队列使用 vb2-vmalloc，支持 MMAP、导出和导入 DMA-BUF。CAPTURE 的 sizeimage 包含
NV12 之后的参考辅助区，bytesused 只包括像素。L0/L1 按标准 DPB 的 reference_ts 查找
已成功解码且 nal_ref_idc 非零的 CAPTURE；重新排队或停流使旧参考失效。
CAPTURE 索引提供稳定图像身份，作业引用与设备映射保持到 reset 成功后才释放；
reset 失败时保留 quarantine 页和 IOVA。

原始 SG 物理范围检查覆盖不同 EXPBUF 对象共享同一存储的别名。输出与输入／参考
必须分离，输入也与参考分离，两个只读参考允许共享。BSM padding 的 CPU 写入位于
别名校验之后。V8 补齐 OUTPUT Request 必需的 buf_out_validate，ANY field 归为 NONE。
V9 支持客户端共同的正负 POC 原点：逐行 IDR top/bottom POC 相等，frame_num 为 0，
对 IDR/P/B 均写入当前 POC；不能硬编码 FFmpeg 的 IDR POC 必须为零。

nextScale=0 的正式验证使用系数 25 编码后、保持解码语义不变地迁入 SPS 的码流，三路相同。

精确用例、哈希及历史失败分类见 [validation-v10.json](validation-v10.json)。完整回执和

## 已核实的控制模型

本轮分析的是固定运行包 `userspace/server-avc-20261103-v7` 中的本机库：

- 文件：`vendor/lib64/libomx_avcdec_hw_sprd.so`，148,856 字节，ELF64 AArch64。
- SHA256：`2d134dd546f7ec028b03e28e1e58c2449ccdb8f64fd32571ee5bcb3460d437b9`。
- 动态符号表有 111 个已定义函数；通过 REA/Ghidra 检查了 7 个函数，并保存完整证据。

| 已检查入口 | 静态观察 |
| --- | --- |
| `VSP_OPEN_Dev` | 打开 `/dev/sprd_vsp`，映射 0x14000 字节；内部保存 `mmap_base - 0x61200000`。 |
| `H264Dec_Read_SPS_PPS_SliceHeader` | 库按 NAL 类型组织 SPS/PPS 和 slice 解析，调用 `read_bits` 及 `H264Dec_Process_slice`。 |
| `H264Dec_Process_slice` | 库执行 picture 初始化、参考列表构造和重排，准备后续解码所需状态。 |
| `H264Dec_init_global_para` | 分配 SPS/PPS、DPB、参考列表等库内状态；函数名不代表全局硬件寄存器配置。 |
| `read_bits` | 轮询硬件 BSM 就绪，写入读取位数并从寄存器取回数据；语法解析使用硬件位读取辅助。 |
| `H264Dec_cfg_bsm` | 配置输入地址、长度及 BSM，可选择 start-code 搜索。 |
| `H264DecDecode_NALU` | 配置参考信息、缩放矩阵等寄存器，启动 slice 数据解码并调用 `VSP_POLL_COMPLETE`。 |

库内形如 `0x6120xxxx` 的常量必须结合上述基址偏置理解，不能当作 W202DS 物理地址。
现有 DTS 中解码核心位于 `0x32200000`。

以下只记录已观察到的寄存器操作，尚不构成完整编程规范：

| 相对 mmap 基址的偏移 | 观察到的用法 |
| --- | --- |
| `0x1080`、`0x1084` | `H264Dec_cfg_bsm` 将同一个库内地址字段右移 4 位后写入；地址字段来源待继续追踪。 |
| `0x8000`、`0x8004` | BSM 输入长度和控制配置；各字段和 padding 要求待进一步核实。 |
| `0x8008` | BSM 位读取控制；`read_bits` 写入位数及触发位。 |
| `0x8010` | `read_bits` 取回数据。 |
| `0x8018`、`0x8020` | BSM 清理/就绪轮询。 |
| `0x1030` | slice 数据解码提交路径写入 10，随后等待完成。 |

据此，库确实承担逐 slice 控制及参考状态管理，原生 stateless 值得优先实现。
但仍需验证如何从客户端给出的 slice/header bit offset 定位 BSM、如何处理防竞争字节、
参考帧辅助数据的格式，以及独立作业是否完整恢复硬件状态；不能据此宣称硬件模型已完全掌握。
原始库、函数分析、汇编和快照仅在本地 `../reference/avc-abi-20261107-v1/` 保存。

本轮真机补充核实：BSM 可从独立 NAL 的头部开始，按 RBSP header bit count 跳过
语法头，再启动 slice 数据解码；`0x1034` 使用去除 emulation-prevention 后的 NAL
字节数。7 个原生 IDR 样本中有 3 个含防竞争字节，1080p 样本含 15 个，像素均一致。
表 RAM 的 MMIO 读回会返回无效值，不能作为重放数据；固定 CAVLC 表从
`VSP_TABLE_TRANSFER` 的 CPU 数据边界验证。参考辅助缓冲在 progressive 模式下
按 `macroblock_count * 80 + 1024` 分配，其他模式尚未纳入原生后端。

CABAC 按 slice 类型、cabac_init_idc 和 QP 生成 454 个初始状态。标准 (m,n) 数据来源于
本树 GPL-2.0 的 `rkvdec-h264.c`，按实际硬件顺序重排；逐项对照原厂七组表完全一致。
原生 Main 96 帧验证通过。标准去块 controls 的 offset_div2 在写寄存器前必须乘 2；
扩展 P 帧测试发现该遗漏，修正后原失败样本的 8 帧全部匹配。表 RAM 的内容仍以
CPU 数据／标准表为依据，不使用无效 MMIO 读回。

B 帧原厂同流对照核实：mode 在 `0x1020` 使用 `0x11020004`，spatial-direct 在
`0x1048` 的 bit 11；L1 稳定图像索引在 `0x1074` 的低六位。L0/L1 的 POC 同在第一组
POC 表中，分别从 `0x1200`／`0x1240` 开始，不能把 L1 POC 写入 `0x2000`。
L1 Y／UV／辅助地址分别从 `0x2480`／`0x2580`／`0x2680` 开始；单项 B 的
短期掩码为 `0xfffefffe`。CABAC 沿用 I 及 init0/1/2 四组标准表，实际 IPB 像素测试均通过。

本轮修改前备份、REA 分析、模块回执和设备证据包最终保存在研究工程
`archive/linux/vpu-v4l2-20261107-v2/`。`userspace/source/` 新增仅供实验的
`w202-avc-trace.c`、`w202-vpu-idr-replay.c`、`w202-vpu-native-idr.c` 和测试流解析头文件。
生产 worker 仅在显式定义 `W202_AVC_TRACE` 时启用观测挂钩，现有设备运行包未替换。

## 实现顺序和验证条件

1. **完成最小硬件控制描述。** 追踪 BSM 定位、slice 参数、参考图像地址、辅助缓冲、
   scaling/CABAC 表、启动及完成路径。将字段与 SPS/PPS、slice 和 DPB 参数逐项对应。
   第一关是脱离原厂库，独立解出已知测试流的一帧、单 slice IDR，并与软件参考逐字节一致。
2. **接入原生 V4L2 stateless。** 使用标准 H.264 controls、Media Request API、
   `v4l2_m2m` 和 vb2，输出 NV12。应用负责码流解析及参考状态，内核负责参数校验和作业执行。
   硬件按 slice 控制，当前只验证单 slice；多 slice 共用 CAPTURE 的流程留待扩展。
   前端、参数到寄存器的 H.264 后端及硬件资源管理分别维护；同一核心只允许一个硬件 owner。
3. **补齐参考帧与生命周期。** 覆盖 I/P/B、显示顺序、DPB 辅助数据复用、stride/crop、
   缓冲引用、seek/flush、异常流、超时、正在 DMA 时取消和恢复。保持 reset 完成后才释放 DMA 缓冲。
   复用现有 VAU/DMA API，vb2 映射和原有手工导入需要明确各自所有权，避免重复映射。
4. **验证真实应用。** 先用确实启用 Request API 后端的播放器构建验证，再核对设备上浏览器的
   实际解码后端；根据需要补 VA-API 接口。验收同时检查应用解码器、VPU 中断、像素输出和
   空闲 PM；安装预编译软件本身不算硬解通过。Vulkan Video 后续复用已掌握的逐帧控制基础。

第 1 步是原生硬件后端的验证条件；未通过前不把接口框架登记为可用解码器。
当前工作从 H.264 progressive 8-bit 4:2:0 开始，其他 codec 和编码分别验证后再报告支持。

## 内核和构建条件

V9 验证所用内核配置已有 `MEDIA_SUPPORT=m`、`VIDEO_DEV=m`、`MEDIA_CONTROLLER=y`、
`VIDEOBUF2_CORE=m` 和 `VIDEOBUF2_V4L2=m`。
`MEDIA_PLATFORM_SUPPORT` 未启用，`V4L2_MEM2MEM_DEV`、`V4L2_H264` 和 vb2 DMA 后端未选中。
本树 6.18 的 Request API 随 Media Controller 编译，**没有独立的
`MEDIA_CONTROLLER_REQUEST_API` 配置项**；不能因该旧配置名缺失而判定 Request API 不存在。

本轮从匹配 6.18 源码独立构建 M2M helper，以 build.mk 声明依赖，vb2 使用现有
vmalloc 后端，H.264 参数构造直接使用本驱动实现；没有混用另一内核的模块或符号基线。
源码位于本工程 `source/`，`build.mk` 声明模块依赖；独立 Kbuild 命令见
[构建说明](README.md#构建)，产物使用显式指定的输出目录。
实际设备测试使用 B 开发环境，旧私有 ABI 路径作为对照保留，硬件所有权不可重叠。
